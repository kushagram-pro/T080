# Faculty Collaboration Network Portal

A web portal where LNMIIT faculty publish their expertise, research interests, projects and
publications, find colleagues to work with, and send structured collaboration requests.
Administrators manage accounts and departments; Research Administration and Department
Management get read-only reports.

## What it does

| Role | Can do |
|---|---|
| **Faculty** | Register (admin approval required), build a profile, search colleagues by expertise / department / designation, see suggested collaborators, send / accept / decline / withdraw collaboration requests, get notifications |
| **Administrator** | Approve or reject registrations, manage accounts and roles, activate / deactivate, manage departments, send password reset links, admin dashboard, audit log |
| **Research Admin** | Browse all active profiles, institute-wide collaboration activity report, any department's summary |
| **Department Management** | Browse profiles, summary report for their own department |

Everyone can reset a forgotten password by email and change their password from the Account page.

## Tech stack

- **Backend:** Python 3.13, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL, bcrypt, JWT (python-jose), SendGrid, slowapi
- **Frontend:** React 19, Vite, React Router (plain CSS, no UI library)
- **Tests:** pytest against a separate PostgreSQL test database

Authentication: a short-lived access token kept in memory by the frontend, plus a refresh token in an
httpOnly cookie that is recorded server-side (so logout, password changes and deactivation revoke it).

## Setup

Commands are for **Windows PowerShell** (macOS/Linux equivalents in comments where they differ).

### Prerequisites

| Tool | Version | Check |
|---|---|---|
| Python | 3.11+ (developed on 3.13) | `python --version` |
| PostgreSQL | 14+ (developed on 18) | `psql --version` |
| Node.js | 20+ (developed on 24) | `node --version` |

### 1. Database

Create an empty database called `faculty_portal`, either in pgAdmin or with:

```bash
psql -U postgres -c "CREATE DATABASE faculty_portal;"
```

### 2. Backend

```bash
cd backend
python -m venv venv
.\venv\Scripts\Activate.ps1          # macOS/Linux: source venv/bin/activate
pip install -r requirements-dev.txt  # app + test tools (requirements.txt is app only)
copy .env.example .env               # macOS/Linux: cp .env.example .env
```

Edit `backend/.env`:

- `DATABASE_URL`: your PostgreSQL user and password. **If the password contains `@`, `:`, `/` or `%`,
  URL-encode it** (`@` becomes `%40`), otherwise the connection fails with a confusing host-name error.
- `SECRET_KEY` and `REFRESH_SECRET_KEY`: two different random values. Generate each with
  `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
- `SENDGRID_API_KEY`: leave empty for local development (see [Email](#email)).

Create the tables, then the first administrator (registration only creates *pending faculty*, so
someone has to be able to approve them):

```bash
alembic upgrade head
python -m scripts.create_admin --email admin@lnmiit.ac.in --name "Portal Admin"
```

The script asks for the admin password. Run it again with the same email to reset that admin's password.

Start the API:

```bash
uvicorn app.main:app --reload --port 8000
```

Interactive API docs: http://localhost:8000/docs

### 3. Frontend

In a second terminal:

```bash
cd frontend
npm install
copy .env.example .env               # macOS/Linux: cp .env.example .env
npm run dev
```

Open **http://localhost:5173** and log in with the admin account.

> Use `localhost` for both, not `127.0.0.1`. The login cookie is set by `localhost:8000`; mixing
> `localhost` and `127.0.0.1` makes the browser treat them as different sites and you'll be logged
> out on every reload.

## Running the tests

```bash
cd backend
.\venv\Scripts\Activate.ps1
pytest
```

- The suite uses a **separate database**: your `DATABASE_URL` database name plus `_test`
  (e.g. `faculty_portal_test`). It is created and migrated automatically, and emptied before each
  test, so tests never touch your real data. It refuses to run against a database whose name
  doesn't end in `_test`. Set `TEST_DATABASE_URL` to use a different one.
- Emails are captured, not sent.
- Each test is tagged with the SRS IDs it verifies, e.g. `@pytest.mark.req("FR-026", "BR-009")`.
  The run ends with a coverage summary, and this writes the traceability table:

```bash
pytest --req-report=../docs/test-traceability.md
```

Current result: **135 tests, all passing; all 44 functional requirements (FR-001 to FR-044) and
19 business rules (BR-001 to BR-019) covered.** See [docs/test-traceability.md](docs/test-traceability.md).

## Email

Emails go out through SendGrid: registration approved / rejected, collaboration request received /
accepted / declined / cancelled, and password reset links.

- **Local development:** leave `SENDGRID_API_KEY` empty. Emails are then written to the backend log
  instead of being sent, including password reset links, so the whole flow can be tested.
- **Real sending:** create a SendGrid API key with "Mail Send" permission, verify the sender address
  in SendGrid, and set both `SENDGRID_API_KEY` and `SENDGRID_FROM_EMAIL`. If SendGrid rejects the key
  (`401 Unauthorized` in the backend log), the key is wrong or revoked.

## Configuration

All settings live in `backend/.env` (see `backend/.env.example`).

| Setting | Default | Meaning |
|---|---|---|
| `DATABASE_URL` | required | PostgreSQL connection string |
| `SECRET_KEY` / `REFRESH_SECRET_KEY` | required | Signing keys for access / refresh tokens (keep secret, make them different) |
| `SENDGRID_API_KEY` | required (may be empty) | Empty = log emails instead of sending |
| `SENDGRID_FROM_EMAIL` | | Verified SendGrid sender address |
| `ALLOWED_EMAIL_DOMAIN` | `lnmiit.ac.in` | Only this domain may register (BR-001) |
| `FRONTEND_ORIGIN` | `http://localhost:5173` | Allowed browser origin (CORS) and base for links in emails |
| `COOKIE_SECURE` | `false` | Set `true` in production (HTTPS only) |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `30` | Access token lifetime |
| `REFRESH_TOKEN_EXPIRE_DAYS` | `7` | How long a login lasts without activity |
| `PASSWORD_RESET_EXPIRE_MINUTES` | `30` | Reset link lifetime |

Frontend settings (`frontend/.env`): `VITE_API_URL` (default `http://localhost:8000`) and
`VITE_EMAIL_DOMAIN` (only used for the hint on the register form).

## Troubleshooting

| Problem | Fix |
|---|---|
| `could not translate host name "...@localhost"` | Your database password contains `@`; URL-encode it in `DATABASE_URL` (`@` → `%40`). |
| `database "faculty_portal" does not exist` | Create it (Setup step 1), then `alembic upgrade head`. |
| New endpoints return 404, or code changes don't show up | The dev server's file watcher stopped noticing changes. Stop it (Ctrl+C) and start it again. If the port is "already in use", an old server is still running; close that terminal or end the process. |
| Logged out on every page reload | Open the site at `http://localhost:5173`, not `127.0.0.1`. |
| "Session expired, please log in again" after updating | Expected once after the server-side session upgrade; just log in again. |
| Emails don't arrive | See [Email](#email); check the backend log for SendGrid errors. |
| `Port 5173 is already in use` / `8000` | Another copy of the server is running. Close it or use a different port. |

## Notes against the SRS

Deliberate choices and additions, for the documentation:

- **Designation** is a fixed list (Professor, Associate Professor, Assistant Professor, Professor of
  Practice, Adjunct Professor, Visiting Faculty) so search can filter by it (FR-019).
- **Search** matches partial words case-insensitively ("learning" finds "Machine Learning"); keywords
  are comma-separated and results are ranked by how many keywords matched.
- **Suggestions** use exact (case-insensitive) keyword overlap, weighted: a keyword that is expertise
  for both people scores 2, any other overlap scores 1.
- **Faculty see only complete profiles** in search (BR-005); Research Admin, Department Management and
  Admins see all active profiles.
- **Sending a request requires having a profile**, so the recipient can see who is asking.
- **Notifications** cover the three BR-018 events plus one added at the team's request:
  *request cancelled*, when a pending request is withdrawn automatically because the other person's
  account was deactivated.
- **Admin-created accounts** are active immediately; self-registered accounts need approval.
- **Rejected applicants** can register again with the same email (the same account returns to pending).
- **Password reset** (not in the SRS) emails single-use links that expire after 30 minutes, only to
  approved, active accounts.
- The SRS traceability matrix (section 23) numbers FRs differently from section 13 (e.g. it splits
  FR-019). The code and tests use the **section 13** numbering.
